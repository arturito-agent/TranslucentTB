# Synthetic native validation evidence

These files record functional cases and separate latency trials. Resource
benchmarks are still in progress. All content was
generated by the repository's synthetic fixtures. Native functional and latency
evidence comes from the isolated Windows VM; the CI harness receipt described
below comes from a separate hosted Windows runner.
No private application data, authentication or host paths are included.

See [environment and limitations](../dynamic-validation.md) before interpreting
the results. A passing color row does not verify glyph contrast or every state.

`live-moves-e4f0.json` and `functional-live-*.csv` / `states-live-*.csv` record
the current e4f09c8 application moving Bottom → Left → Right while retaining
one owned process per capture backend. All 36 exact-color cases and 30
Maximized Clear / Desktop Dynamic stages pass. During each measured inactive
stage, attempts and completed frames do not advance, the capture timer is
stopped, and the bounded discovery timer is not queued. Both owned application
processes exit gracefully. These short functional checks establish neither
resource budgets nor the rare delayed-discovery recovery branch.

`functional-*.csv` compares the expected color, worker's confirmed RGB and a
physical pixel on the real taskbar. RGB values are decimal 0xRRGGBB. `captures`
in these early fixtures means sampling **attempts**, not completed DXGI frames.
`run_length` is physical steps, not the total frequency of a color. Rectangle
right/bottom bounds are exclusive. `-125` records 125% scale; other files use
100%. The reference display remains 1280x800.

`states-*.csv` records Desktop Dynamic / Maximized Clear and a visible-window
title rule that alternates Dynamic/Clear. Attempts must remain unchanged during
the measured part of each Clear stage and advance during Dynamic. Sizable
window frames can be unreliable input: before any confirmed color, Dynamic
must render the known fallback RGB 32,48,64. This is checked explicitly rather
than assuming the client background extends through a native window frame.

`display-off-*.json` records the actual display-off command and subsequent
console-key wake. Off-state timer=0, paused=1 and unchanged attempts are checked;
after waking, timer=1, paused=0 and increasing attempts are required.

QPC ticks and frequency are the Windows monotonic clock, shared across processes.
Do not interpret them as UTC. Short functional stages do not establish CPU/RAM, stability or energy results.
The focus-latency CSVs and focus-latency-a1b0.json use 30 jittered trials per
backend, a 50ms observer and nearest-rank p95. They include the DXGI maximum
outlier and identify the exact application revision and geometry.

`refresh-race-a1b0.json` is a negative control: bounded overlapping forced-refresh
and sent timer messages leave the classic-taskbar sampler stopped while not
paused. It records a reproduced defect, not a passing result or resource trial.
`refresh-race-right-*-b464-r*.json` records three fixed-revision trials per
backend, each with active timers and increasing attempts after the overlap.
`functional-right-*-b464.csv` records the six color cases per backend after that
fix. These short tests do not establish resource budgets or prolonged stability.

`fixture-check-ci-1851.json` records Windows PowerShell compile/protocol/lifecycle
checks on GitHub-hosted Windows Server 2025. Uniform has zero animation ticks;
Changing and Interaction produce repeated paints at a nominal33ms timer interval.
Counts describe callbacks, not monitor presentation. This checks test tooling
only and establishes no application resource result or local VM preflight.

`stopped-dxgi-b464.json` retains the first invalid target observation from the
new full series. Sampling stopped during warmup without a paused flag or capture
failure. The collector aborted before writing that batch's GPU stream. This is
failure evidence, not a passing result, complete comparison or established cause.

`fixture-check-vm-1851.json` records the same workload lifecycle preflight on the
actual Windows11 VM, without TranslucentTB running. The static scene does not
animate; the changing/interaction scenes produce repeated paints. Native file
transport changed line endings to CRLF; canonical LF text was matched to source.
This is workload evidence only, not a backend/resource comparison.

`policy-recompute-{gdi,dxgi}-51b4-negative-r1.json` records controlled negative
results for transient teardown. GDI records 64 stops and DXGI 58. `passed=true`
means the requested bad behavior was observed: unwanted timer stops with
suppression bit4, followed by an active sampler. The probe's
synthetic unlock notifications do not change the Windows session lock state.
It establishes neither the cause of the spontaneous stop nor a resource budget.

`policy-recompute-{gdi,dxgi}-753a-positive-r{1,2,3}.json` records three positive
trials per backend after separating shutdown from temporary suppression. All
have zero stops, active timers, advancing attempts and zero IPC errors.
`refresh-race-{gdi,dxgi}-753a-r1.json` also verifies the original timer/refresh
overlap on that revision. `functional-right-{gdi,dxgi}-753a.csv` contains its six
color cases per backend on the real right taskbar. These controlled regressions
do not establish long-series health or resource budgets.

`inactive-gdi-753a.json` deliberately asks the collector to require Dynamic
while Desktop Clear is selected. Its expected rejection and failure-only
scheduler snapshot pass; capture attempts and frames remain zero. This is a
diagnostic-tool check and inactive-mode test, not an application failure.

`smoke-right-scheduler-753a.json` summarizes the five-phase, 90-second-per-phase
right/static diagnostic. Exact physical geometry, healthy sampler progression,
zero scheduler stops/creation failures, matching scoped GPU batches and all
graceful target exits pass. Its short warmup and SMOKE labels exclude it from
resource budget claims.

`states-right-gdi-753a-startup-overlap.csv` retains a failed state-test assertion
during Explorer's delayed startup reconstruction. The last actual background
is the configured fallback while lifetime RGB still refers to pre-reset state.
`states-right-gdi-753a-settled.csv` passes the unchanged assertions after shell
startup settles. These do not establish complete reconstruction recovery or
the full current state matrix; see the validation notes.

`states-right-gdi-753a-start-button-probe.csv` retains the original failing Start
pixel assertion. `start-pixel-gdi-753a.json` shows that its leading-edge probe
hits the pressed Start button, while the fixed middle background point shows
the exact expected RGB. The updated state harness records probe coordinates
and window class and keeps the same exact color criterion. This diagnostic
does not by itself establish the full positive state matrix.

`states-right-753a.json` now binds all ten positive cases and the executed helper
hash: five state cases per backend, each with five alternating stages. The
`states-right-{gdi,dxgi}-{case}-753a.csv` files record exact background pixels,
sampler behavior, probe coordinates/class and foreground identity. This is
classic right-taskbar integration evidence at 100%, not complete menu/battery
saver/rule-form coverage or a resource measurement.

`explorer-recovery-gdi-753a.json` records a real Explorer restart with the GDI
app kept alive, resumed sampling/completed frames and exact blue taskbar
rendering afterwards. A transient stop while the taskbar map is empty is
retained. The receipt binds the same app PID and its graceful exit. It does
not establish other positions or recovery scenarios.
`explorer-recovery-dxgi-753a.json` now records the separate passing DXGI run,
including 27 observations with an empty map and stopped sampler before recovery.
The receipts retain first-observed-new-frame elapsed values, approximately
5.8s GDI and 32.0s DXGI, with the single-trial/QPC/observer limitations stated.
`explorer-recovery-left-{gdi,dxgi}-753a.json` records both passing left cases,
their actual bounds, exact pixel, owned exits and first new frame observations
(about 5.8s GDI, 4.7s DXGI). These single observations do not establish recovery
percentiles or an API performance ranking.
`explorer-recovery-bottom-gdi-753a-failed.json` preserves the failed bottom
case: the real bar keeps the old blue pixel while its worker has no taskbars,
timer=0, paused=0 and unchanged attempts/frames. It is failure evidence and
does not establish the exact transient classification cause. DXGI was not run
after this failure. `explorer-recovery-bottom-{gdi,dxgi}-e4f0.json` records the
first nominal passing repeats on the new source, including settled discovery
timers and verified exits. Their request counters are both zero: the actual
delayed-retry path is not exercised and the rare failure's repair is unproven.

`functional-matrix-e4f0.json` binds both executable hashes, actual bounds and
four verified exits for the new left/bottom runs. The four
`functional-{left,bottom}-{gdi,dxgi}-e4f0.csv` files each contain six exact color
cases. This is functional/geometry evidence at 100%, not CPU/RAM, stability or
glyph-contrast evidence.
